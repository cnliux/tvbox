## 一、先看结论：清单背景与真实代码的偏差

这份提示词集合整体成立，但有几处前提与实际仓库不一致，开工前必须先校准，否则改造方案会落错位置。

| # | 提示词中的前提 | 仓库实际情况 | 影响 |
|---|---|---|---|
| 1 | 「ui 层 Compose 页面直接依赖仓库」 | 页面主要依赖 `ui/TvBoxViewModel.kt`；仓库由 `MainActivity` 中的 `TvBoxViewModelFactory(this)` 手动构造后注入 ViewModel | 1.1 的真正耦合点是 **ViewModel → data 实现类**，不是页面 → 仓库；接口抽到 domain 后，改造重点在 ViewModel 与工厂 |
| 2 | 「domain/useCase 需要新建」 | `domain/` 已有 30+ 个纯逻辑类（`SearchMerge`、`PlaybackRecovery`、`LiveLineFallback`、`PlaybackSelection`、`PlayerController` 等），并有 40 个 JVM 单测覆盖 | 不是从零建 domain，而是**把 ViewModel 里残留的编排收敛进已有 domain**，并补 useCase 这一层命名 |
| 3 | 「并发工具需要从零抽出」 | 已有 `Semaphore(3)`（`TvBoxViewModel.kt` 约 2912 / 2990 行）、`withTimeout`、`awaitAll`、`relaunch()` 取消旧 Job、`ConcurrentCollections.kt`（退避 + 安全集合）、`SearchMerge.kt`（增量去重）、`LiveLineFallback.kt`（Error/Stall/Ended 三态）、`FlvContinuityProxy.kt`（时间戳续接） | 1.3 是**收编散落实现 + 补单测**，不是新写一套；2.3 的「三态换线」也已有雏形 |
| 4 | 「Application 里有阻塞初始化」 | `TvBoxApplication.onCreate()` 只有 `CrashHandler.install(this)`，Application 本身几乎无阻塞 | 1.4 的排查对象应改为 `MainActivity` 的 ViewModelFactory 与 `TvBoxViewModel.init{}`（约 380 行起） |
| 5 | 「若项目已有 benchmark，补 macrobenchmark」 | `settings.gradle.kts` 只有 `include(":app")`，无 benchmark 模块，依赖里也没有 macrobenchmark | 1.2 的第 4 项需要**新建模块 + 加依赖**，属于独立工程，不宜混入页面 patch |
| 6 | 「runTest 单测」 | `testImplementation` 目前只有 `libs.junit`，version catalog 里只有 `kotlinx-coroutines-android`，没有 `kotlinx-coroutines-test`，也没有 Turbine | 1.3 的 `runTest` 用例需先在 `libs.versions.toml` / `build.gradle.kts` 加测试依赖；否则只能按提示词用 Channel 手写 |
| 7 | 「token 化从零做」 | `ui/theme/Theme.kt` 已有 `TvColorTokens`、`Typography`、`staticCompositionLocalOf`，两种主题共用一套 token 映射 | 3.1 已有约一半基础，缺的是圆角 / 间距 / 焦点描边 / 动效时长与三态组件 |
| 8 | 「data 层职责混杂」 | 成立。`data/` 共约 5357 行，混有 API（`MacCmsApi`）、仓库（多个 `Repository`）、本机存储（多个 `Store`）、代理（`FlvContinuityProxy`）、服务（`RemoteManageServer` 593 行、`UpdateDownloadService`）、投屏（`DlnaCaster`）、导出器 | 1.1 的问题清单成立，但「不大改包结构」与「data 只保留数据获取」存在张力，需要先定边界 |

规模参考：`TvBoxViewModel.kt` 4385 行、`TvBoxApp.kt` 2541 行、`PlayerChrome.kt` 1832 行、`MobileLiveScreen.kt` 1547 行、`MovieRepository.kt` 615 行。1.1 / 1.2 的「父 State 过大」「编排混在同类」判断属实。

## 三、开工前需要先定的四件事

1. **1.1 的边界**：提示词要求「保持 public API 不变、ui 调用点仅改 import」，但 `TvBoxViewModel.kt` 4385 行承担了全部编排。需要明确是「只抽仓库接口到 domain」还是「同时把 ViewModel 编排下沉到 useCase」——后者的改动量远超「最小改造」。
2. **1.3 的测试依赖**：`runTest` 需要 `kotlinx-coroutines-test`；若坚持不加依赖，则按提示词用 Channel 手写收集，两种路径的验收形式不同。
3. **1.2 的 benchmark 归属**：新建 `:benchmark` 模块会改动 `settings.gradle.kts` 与 CI 构建流程，建议单独排期，不与页面 patch 混在一起。
4. **1.4 的 keep 规则**：`app/proguard-rules.pro` 中 `-keep class com.tvbox.app.ui.** { *; }` 为 Baseline Profile 全量保留 UI 包（工程内还依赖 `androidx.profileinstaller`）。这是体积项里最明确的可评估点，但收紧需同步验证 profile 生成，风险高于其他项。

【背景】项目结构为 app/src/main/java/com/tvbox/app/{data, domain, ui}，当前 data 层聚合了 API、仓库、历史、OTA、直播数据等多种职责，ui 层 Compose 页面直接依赖仓库。

【任务】
1. 扫描 data 包，识别「网络请求 + 缓存 + 业务编排」混在同一类中的文件，列出问题清单；
2. 对每个文件给出最小改造方案：把编排逻辑下沉到 domain/useCase（如 GetHomeFeedUseCase、ResolveLiveStreamUseCase），data 只保留数据获取；
3. 定义仓库接口（如 VideoSourceRepository、HistoryRepository、LiveRepository）放到 domain，实现类留在 data；
4. 输出改造后的文件树 diff（新增/移动/重命名），并说明没有 DI 框架时如何用手动构造的工厂组织依赖。

【验收】问题清单、逐文件改造方案、完整 diff、回归测试清单（手工 + 单测）。

#### 1.2 Compose 重组性能审计

你是 Jetpack Compose 性能优化专家，处理仓库 https://github.com/cnliux/tvbox。

【背景】首页影视列表展示豆瓣热播（海报/评分/分页/焦点高亮），TV 端靠遥控器焦点移动；详情页后台补齐播放源；搜索页最多 3 源并行增量去重。这些页面在低端盒子上容易出现过度重组与焦点抖动。

【任务】
1. 审计首页影视列表 / 「继续观看」卡片、详情页（主源优先 + 后台补齐）、搜索页（3 源并发增量合并）、播放页操作栏（遥控器焦点切换）的重组来源。
2. 对每个页面列出：
   - 未使用 remember/derivedStateOf 导致的重复计算；
   - 父 State 过大导致整棵子树重组（建议拆成细粒度 state holder）；
   - LazyColumn/LazyRow 中缺少 key 或用非稳定 lambda；
   - 焦点系统（FocusRequester/focusProperties）引发的无谓重组或焦点抢占。
3. 给出可直接应用的 patch，并为每处标注「预期收益（重组次数/帧时间）」。
4. 若项目已有 benchmark，补充一个 macrobenchmark 用例度量首页首帧与滚动卡顿（FrameTimingMetric）。

【验收】审计清单表 + patch + 验收指标（重组次数下降比例、帧时间对比）。

#### 1.3 并发与协程规整

你是 Kotlin 协程与并发专家，处理仓库 https://github.com/cnliux/tvbox。

【背景】搜索页「最多三条来源并行，结果增量去重显示」；详情页「后台补齐播放源和选集」；直播「主源不可用时自动尝试备用源」「线路异常时自动换线」；虎牙 FLV 本机代理需在上游被关流后重新解析续拉。这些是并发正确性高风险点。

【任务】
1. 找出所有涉及并发的位置（搜索多源合并、详情补齐、直播备用源切换、FLV 代理续拉、OTA 后台下载）。
2. 针对每处回答：
   - 当前使用的 scope/调度器是否合理（是否误用 GlobalScope、Dispatchers.Main 跑 IO）；
   - 失败与超时是否有结构化处理（supervisorScope、withTimeout、Semaphore 限流）；
   - 取消传播是否正确（页面退出时能否及时取消未完成请求）。
3. 给出改造 patch，重点：
   - 为「多源并行」抽出统一的 fan-out/fan-in 工具函数，带 per-source timeout 与「先到先显示」的增量回调；
   - 直播换线逻辑显式区分「用户主动切」与「异常自动切」，避免两条路径重复请求；
   - FLV 续拉保证「重解析期间不丢失旧帧缓冲且时间戳严格单调」。
4. 为上述并发工具补充 JVM 单测（runTest，必要时用 Channel 手写收集）。

【验收】问题清单 + patch + 单测 + 并发时序说明（关键路径的 CancellationException 处理）。

### 二、功能增强类

#### 2.1 播放器能力增强

你是 Media3/ExoPlayer 专家，处理仓库 https://github.com/cnliux/tvbox。

【背景】播放器基于 Media3 ExoPlayer，自行处理遥控器快退/快进 10 秒、长按、切集、倍速、自动跳下一集、手机手势；画面比例支持自适应/裁剪/拉伸并本机记忆；播放亮屏与音频焦点中断暂停已有实现。

【任务】按优先级实现（先给设计，再给 patch）：

#### 2.2 源管理与导入体验增强

你是 Android 产品 + 客户端工程师，处理仓库 https://github.com/cnliux/tvbox。

【背景】项目不内置视频源，全部由用户导入（订阅地址、扫码、JSON 文件）；设置页「视频接口」可选首页/搜索数据源；添加接口时电视弹二维码、手机扫码填写后同步；手机版为页内管理。

【任务】增强源管理：

   - 订阅地址拉取失败时给出分类错误提示（DNS/超时/非 JSON/格式不合法），并保留上次成功配置；

2. 多源可用性体检：
   - 对已导入的 MacCms 接口做轻量探活（首页分类 + 一个搜索），结果以状态标签展示，可手动/定时刷新；

3. 源排序与权重：用户可置顶/拖拽排序，搜索并行时按权重分配超时。
4. 配置备份/恢复：导出当前源配置为 JSON（不含密钥），支持分享口令或文件。

【验收】交互流程图 + 状态层 API + 关键 diff + 遥控器可操作性核对清单。
